# Xiaomi/Mijia MCL02M — локальное управление и UI: углублённый разбор

Дата: 2026-08-21
Объект: интерфейсная ESP32-плата с `ESP-WROOM-32D`, модель приложения `chunmi.ihcooker.v2`
Режим: статический анализ полного 16 MiB flash dump, без записи, без отправки команд нагрева.

## 1. Границы и степень доказанности

Целенаправленно разобраны только локальные функции: I²C с силовой платой, нагрев, два кольца, измерительные каналы, аварии, дисплей, клавиши, энкодер/touch-путь, подсветка и buzzer. Реализацию беспроводного подключения, облачную часть, MIoT-транспорт и рецептурные данные в этот документ не включал.

Обозначения:

- **Высокая уверенность** — следует непосредственно из кода и повторяющихся вызовов.
- **Средняя уверенность** — кодовая ветка ясна, но физическое имя сигнала требует корреляции с платой.
- **Низкая уверенность** — возможная трактовка по косвенным признакам; не использовать как спецификацию без измерения.

Доказательные файлы:

- `work/cookstep_hidden.c` — восстановленный основной цикл CookStepTask (`FUN_401542b0`);
- `work/period250_hidden.c` — Period250MsTask (`FUN_4015af48`);
- `work/keyscan_hidden.c` — KeyScanTask (`FUN_401931b4`);
- `work/incident_hidden.c` — IncidentTask (`FUN_4015700c`);
- `work/ghidra_decompile/all_functions.c` — полный экспорт декомпиляции;
- `reports/MCL02M_static_reverse_engineering.md` — общий отчёт по дампу;
- `diagnostics/heating_test_2026-08-15_trip3_report.md` — реальная пассивная тепловая проверка.

## 2. Архитектура задач и время

Приоритеты FreeRTOS (меньшее число — меньший приоритет в данном вызове создания задач):

| Задача | Функция | Приоритет | Роль |
|---|---:|---:|---|
| `UartListenTask` | `FUN_401517cc` | 8 | входящие события, не нужен для собственной локальной прошивки |
| `UartSendTask` | `FUN_401532f4` | 7 | штатная внешняя телеметрия, не нужен |
| `KeyScanTask` | `FUN_401931b4` | 5 | GPIO/touch, debounce, long-press |
| `IncidentTask` | `FUN_4015700c` | 6 | UI state machine и отображение |
| `CookStepTask` | `FUN_401542b0` | 4 | I²C, ошибки и формирование управляющих байтов |
| `Period250MsTask` | `FUN_4015af48` | 3 | таймеры шагов, переходы состояний, периодическое обновление |
| `Period1MsTask` | `FUN_40155964` | 2 | быстрые экранные/временные обновления |
| `PeriodBuzzerTask` | `FUN_40192d0c` | 11 | очередь звуковых паттернов и PWM |

`CookStepTask` заканчивает проход задержкой `FUN_40091c5c(..., 5)`. Это 5 системных FreeRTOS ticks, а не гарантированно 5 ms; фактический период надо подтвердить логическим анализатором. `Period250MsTask` заканчивает проход задержкой `0x19` ticks и по имени/структуре является 250-мс задачей. Внутри неё счётчик 60 событий уменьшает секунды/таймеры; это означает, что пользовательские секунды формируются не напрямую из I²C-периода.

## 3. I²C-интерфейс силовой платы

### 3.1. Шина и формат кадра

I²C0: SDA GPIO13, SCL GPIO15, pull-up включены, настроенная частота 10 kHz. Адрес силовой платы — `0x54` для записи; read-адрес на физической шине будет `0x55`.

Чтение регистра `r` (`FUN_401939fc`):

1. START, адрес `0x54` + write, байт `r`, STOP.
2. Задержка 3 ticks.
3. START, адрес `0x55` + read, два байта: `value`, затем checksum, STOP.
4. Ответ принимается, если checksum равен `value + r` либо младшему байту этой суммы.
5. Таймаут отдельной I²C-операции — 5 ticks.

Запись (`FUN_40193a8c`) передаёт два байта данных и также проверяет завершение операции с таймаутом 5 ticks.

### 3.2. Реальная последовательность опроса

`DAT_3ffc049c` — индекс конечного автомата. В штатном цикле последовательно читаются:

| Регистр | Переменная | Что можно утверждать |
|---:|---|---|
| `0x20` | `DAT_3ffcf2a0` | основной status/error byte; на нём построен self-check аварий |
| `0x21` | `DAT_3ffcf2a2` | вспомогательный измерительный байт |
| `0x22` | `DAT_3ffcf2a4` | вспомогательный измерительный байт |
| `0x23` | `DAT_3ffcf2a6`, raw `DAT_3ffcf2a8` | второй температурный/измерительный канал с lookup при готовом типе платы |
| `0x24` | `DAT_3ffcf2a7`, raw `DAT_3ffcf2a9`, duplicate `DAT_3ffcf2aa` | преобразованный нижний температурный канал; MIoT P3.7 |
| `0x25` | `DAT_3ffcf2ac` | дополнительный статус/канал |
| `0x26` | `DAT_3ffcf2ab` | флаг/дополнительный канал, участвует в ограничении мощности |
| `0x27` | `DAT_3ffcf2ad` | флаг/дополнительный канал |
| `0x28`, `0x29` | `DAT_3ffcf298`, `DAT_3ffcf299` | тип и готовность силовой платы |
| `0x2A`, `0x2B` | `DAT_3ffc04e9`, `DAT_3ffc04ea` | дополнительные параметры |
| `0x2C…0x2F` | `DAT_3ffc04f1…f4` | четыре сервисных канала, читаются в особом состоянии |

На старте `FUN_40153b7c` читает `0x25`, несколько раз проверяет `0x28/0x29`, затем читает `0x24` и проверяет `0x2A/0x2B`. При десяти неудачных стартовых проходах выставляется коммуникационная ошибка `0x0B`.

Сбой checksum одного регистра не считается мгновенной катастрофой. Счётчик повторов равен 30 в специальном режиме и 500 в обычном; только после исчерпания появляется ошибка связи.

### 3.3. Единственный найденный путь управления нагревом

Статически найдены только три вызова записи в I²C0, все внутри `FUN_401542b0`:

```text
write reg 0x0D: [DAT_3ffc049b, DAT_3ffc049b + 0x0D]
write reg 0x00: [DAT_3ffc049a != 0, (first byte + 0x00)]
write reg 0x0C: [DAT_3ffc049a, DAT_3ffc049a + 0x0C]
```

`DAT_3ffc049a` — младший байт требуемого уровня мощности/gear. `DAT_3ffc049b` — управляющий байт с разрешением и битами выбранного кольца. Для новой прошивки это минимальный локальный протокол, который нужно повторить после пассивного снаффинга; отправлять эти кадры в текущем эксперименте не следует.

## 4. Кодирование мощности и двух колец

### 4.1. Формирование управляющего слова

`FUN_40155628` перед вычислением кольца задаёт базовое `DAT_3ffc049b = 0x81`, затем `FUN_40154b20` выбирает `DAT_3ffcf38c ∈ {0x40, 0x80, 0xC0}`. Кодирование:

- выбран режим `0x80`: устанавливается bit `0x20`, bit `0x40` очищается;
- выбран режим `0x40`: bit `0x40` устанавливается, bit `0x20` очищается;
- выбран режим `0xC0`: устанавливаются оба бита.

Типовые байты управления поэтому выглядят как `0xA1`, `0xC1`, `0xE1` (плюс вариант выключения/переходного состояния). Это **доказано на уровне кодирования**, но соответствие `0x40`/`0x80` конкретно внутреннему или внешнему кольцу по одному ELF не доказано.

### 4.2. Таблица выбора кольца

Для `step[0] & 0xC0 == 0x80`:

- gear `< 0x24` (36): режим `0x80`;
- `0x24…0x37` (36…55): режим `0x40`;
- `>= 0x38` (56): оба, `0xC0`.

Для `step[0] & 0xC0 == 0xC0`:

- `< 0x24`: `0x40`;
- `0x24…0x37`: `0x80`;
- `>= 0x38`: оба.

Для `step[0] & 0xC0 == 0x40`:

- `< 0x1A` (26): `0x80`;
- `0x1A…0x37`: `0x40`;
- `>= 0x39` (57): оба.

При динамическом режиме `step[0] & 0xC0 == 0` сначала используется `0x80`, затем после времени/условия переключение на `0x40`; gear ограничивается диапазоном 25…55. Если `DAT_3ffcf2ab == 1`, уровень принудительно ограничивается `0x23` (35) и выбирается `0x80`.

Окончательно значение мощности может быть обнулено, если истёк `step[7]`/`step[8]` timer. Для одного сценария алгоритм не гарантирует непрерывное PWM-управление: он выдаёт дискретный gear и передаёт его силовому MCU.

### 4.3. Формат записи шага

Текущий шаг — 9 байт по адресу `_DAT_3ffcf398 + index*9`:

| Байты | Значение |
|---|---|
| `step[0]` | флаги шага и режим колец (`& 0xC0`), биты завершения (`0x01`, `0x02`, `0x08`, `0x10`) |
| `step[1:2]` | длительность: положительный `step[1]` — секунды, отрицательный — минуты (`×60`) |
| `step[3]` | верхний порог температуры |
| `step[4]` | нижний порог температуры |
| `step[5]` | желаемый gear |
| `step[6]` | дополнительное время/порог |
| `step[7]` | задержка/событие кольца |
| `step[8]` | второй задержанный параметр кольца |

При смене шага `FUN_40155428` обновляет световой уровень; нулевой gear вызывает `FUN_40192f24`, ненулевой — `FUN_40192ff0`.

## 5. Реальный алгоритм нагрева: это не классический PID

`FUN_40155518` выбирает один из трёх кусочно-заданных алгоритмов (`FUN_40154d2c`, `FUN_40154f30`, `FUN_401550b4`) по `(DAT_3ffcf2b7 & 0x1F)-1`. В бинарнике нет набора коэффициентов `Kp/Ki/Kd`, интегратора, производной и антиwindup, характерных для PID.

Что реально есть:

1. Шаговый gear из 9-байтной записи.
2. Ограничение gear при приближении к нижнему/верхнему температурному порогу.
3. Гистерезис: если текущая температура приблизилась к target примерно на 5 единиц и gear выше 45 (`0x2D`), gear ограничивается 45; снятие ограничения происходит только после ухода ниже target примерно на 7.
4. При специальном flag `step[0] & 0x08` цель уменьшается на 10% для низких целей и на 5% для высоких; gear принудительно сводится к 10 или 45.
5. При `step[0] & 0x18 == 0x18` gear фиксируется `0x46` (70).
6. Отдельная коррекция по `DAT_3ffcf2a6`: ниже `0x60` (96) и около `0x5A…0x65` (90…101) gear ограничивается 10/20; выше `0x65` вводится ограничение 20/85. Точный физический канал этой переменной должен быть подтверждён runtime-корреляцией.
7. `FUN_4015579c` отслеживает изменение температуры и считает канал стабилизировавшимся, если разница меньше 4 единиц.

Это даёт понятную модель для собственной прошивки: быстрый внешний контур может выбирать желаемый gear, но силовая плата сама остаётся ответственна за ток/коммутацию ключей. Если нужен свой PID, его следует строить уже в новой ESP32-прошивке поверх измеренных IGBT/NTC значений, сохраняя аппаратные защитные ограничения.

## 6. Температуры, NTC, IGBT и no-pan

### 6.1. Нижний NTC

Регистровый канал `0x24` преобразуется lookup-таблицей в `DAT_3ffcf2a7` и дублируется в `DAT_3ffcf2aa`. Именно `DAT_3ffcf2a7` возвращается свойством `S_3.Custom/P_3_7_Temperature`, которое в диагностическом мониторе называется `bottom_temperature`. Поэтому связь `0x24 → нижний NTC/нижняя температура` имеет высокую уверенность.

Lookup:

- raw `< 0x0B` → `0xFA` (специальный высокий/невалидный код);
- raw `0x0B…0xFB` → таблица;
- raw `>= 0xFC` → `0`.

В этой ветке есть два уровня порогов:

- `DAT_3ffcf2a7 >= 0xE1` (225) или `DAT_3ffcf2aa > 0xE0` — аварийная температурная ветка силовой платы;
- рабочие ограничения `DAT_3ffcf385`/`DAT_3ffcf384` — пороги конкретного шага, не универсальная температура отключения.

Значения `0xE1…0xFA` — внутренние коды/верхняя область таблицы, не следует без проверки считать их 225…250 °C.

### 6.2. IGBT self-check

Сервисный action `SIID 3 / AIID 15`, вход `PIID 36`, команда `4`, возвращает `PIID 37` — температуру IGBT либо `-1`/`-2` для open/short. Это отдельный диагностический путь, а не прямой getter P3.7. Статика уверенно показывает наличие этого интерфейса; какой именно байт силовой платы лежит под action, без кода силового MCU не доказано.

Полная таблица штатных диагностических команд (полезна только как справочник уже существующей логики, не как требование сохранять старый протокол):

| `selfcheck-cmd` | Смысл |
|---:|---|
| `1` | входное напряжение |
| `3` | нижний NTC |
| `4` | температура IGBT |
| `5` | коммуникация с силовой платой |

В собственной прошивке эти четыре измерения лучше представить как локальные диагностические endpoints и не привязывать их к старым внешним service/property ID.

Практическая runtime-корреляция уже есть: в тесте 2026-08-15 IGBT рос плавно с 51 до 109 °C, а при E-07 одновременно фиксировались status 8 / error 7 / fault 7. Это подтверждает, что E-07 — реальная авария IGBT-сенсора/перегрева, а не случайный обрыв телеметрии.

### 6.3. Контроль «нет посуды»

`DAT_3ffcf2a0 == 0x02` накапливается отдельным счётчиком; после более чем 5 последовательных samples вызывается ошибка code 2. В переданном плане диагностики code 2 соответствует `NoPan`; это высокоуверенное сопоставление по внутренней модели, но окончательное имя raw status требует одной пассивной записи при снятии кастрюли.

Важно: код не реагирует на один случайный байт. Для большинства аварий порог — более 10 повторов (приблизительно 11 последовательных анализов status/температуры), после чего устанавливается ошибка и запускается UI/buzzer.

### 6.4. Карта устойчивых аварий

| Условие в коде | Внутренний error code | Звуковой код | Надёжность трактовки |
|---|---:|---:|---|
| status `0x02` дольше порога | 2 | штатный error path | высокая для code, средняя для имени NoPan |
| status `0x0B` | 3 | 2 | высокая |
| status `0x0C` | 4 | 3 | высокая |
| temp `0x24` в аварийной области / status `0x1B` | 5 | 4 | высокая для ветки |
| status `0x17` | 7 | 5 | высокая; runtime E-07 подтверждён |
| status `0x19`, `0x1A`, `0x1C`, `0x1D`, либо расхождение каналов `>0x31` | 10 | 7 | высокая для ветки |
| status `0x15`, `0x16`, `0x18` | 8 | 6 | высокая |
| status `0x01` | 12 | отдельная ветка | высокая |

Имена из строк ELF: `Hvprotection`, `Lvprotection`, `Botsensorhigh`, `Igbtsensorhigh`, `Igbtsensorbad`, `Bottomsensorbad`, `Communicatebad`, `Wirebroken`. Но raw status→строка проходит через очередь/таблицу событий, поэтому не все названия можно честно привязать к одному байту без runtime-лога.

## 7. Вентилятор и охлаждение IGBT

В приложении ESP32 не найден прямой GPIO/PWM путь к вентилятору. Найденные прямые выходы — buzzer GPIO23, OLED DC GPIO26, GPIO22/GPIO32 и программный LED-драйвер GPIO17/16/4. Команд записи силовой плате всего три (`0x0D`, `0x00`, `0x0C`), и отдельного fan register в ESP32-части нет.

Вывод: вентилятор почти наверняка включается и регулируется силовым MCU/его аналоговым драйвером по собственной температурной логике. Раздел `mimcu` в ESP32 dump полностью `FF`, поэтому прошивку этого контроллера извлечь нельзя. Новая ESP32-прошивка сможет пользоваться штатным автоматическим вентилятором только если силовой MCU продолжит его обслуживать; принудительный fan override потребует отдельного обнаружения команды/линии на силовой плате.

Пассивный тест показал: после E-07 при IGBT около 54…55 °C вентилятор стал неслышен, но нижний NTC оставался около 88 °C. Это говорит о гистерезисе отключения вентилятора по IGBT/силовому радиатору, а не о полном охлаждении всей нижней части.

## 8. Дисплей и графический интерфейс

OLED-путь использует SPI host 1 с частотой 2 MHz: `MOSI=GPIO27`, `SCLK=GPIO25`, `RESET=GPIO26`, `D/C=GPIO33`. Буфер — `0x40 × 6` байт, команда multiplex `0x2F` соответствует размеру 64×48. По конфигурации SPI наиболее вероятен `CS=GPIO0`, но его надо подтвердить прозвонкой flex-шлейфа.

Рендереры:

- `FUN_4019271c` — очистка прямоугольника;
- `FUN_40192790` — копирование bitmap в framebuffer;
- `FUN_401927e0` — blit bitmap с вертикальным смещением;
- `FUN_40155db8` — вывод десятичного числа по цифрам;
- `FUN_40155cb0` — вывод упакованного текста/bitmap-кода;
- `FUN_40155b30` — вывод одного glyph.

Текст на экране в основном не ASCII-строки, а упакованные bitmap/wordcode-ресурсы в `icon1`/`wordcode1`. Для англо-русской прошивки это хорошая новость: не нужно сохранять китайский UI; можно заменить таблицу glyph/bitmap и оставить аппаратный рендерер или написать новый framebuffer-слой.

Из `IncidentTask` уже видны реальные экраны:

| UI state | Что рисуется |
|---:|---|
| 1 | стартовый экран/параметры, две пары двухзначных значений |
| 2 | переходный экран/очистка framebuffer |
| 3 | параметр `DAT_3ffcf2a4 + 0x32` и код состояния |
| 4 | `DAT_3ffcf2a7` и `DAT_3ffcf2aa` — два температурных поля |
| 5 | возврат к стартовому/сервисному экрану |
| 6 | `DAT_3ffcf2a6` и `DAT_3ffcf2a7` |
| 7–8 | сообщение/состояние запуска и stop |
| 9 | изменение первой настройки, диапазон до 210 (`0xD2`) |
| 10 | изменение второй настройки, диапазон до 210 |
| 11 (`0xB`) | сервисные поля `049a`, `2ab`, `2ad` и дополнительные байты |
| 12–13 (`0xC/0xD`) | countdown/error-пути |
| 14–17 | завершение, редактирование и сервисный просмотр |

`FUN_40153d08(code)` переводит UI в состояние ошибки и выбирает bitmap по индексу `(code + 0x110)` в таблице ресурсов. Это удобный механизм для собственной локализации: можно оставить error code API, но заменить bitmap на английские/русские короткие надписи.

## 9. Клавиши, touch и энкодер

`KeyScanTask` — конечный автомат, а не единичный GPIO-read:

- основной цифровой вход читается на GPIO34;
- отдельный touch/key-периферийный ответ читается через `FUN_40193b24(0xC0, …)` либо альтернативную ветку UART1/I²C1;
- сырые touch-коды `0x13`, `0x16`, `0x12` нормализуются в логические клавиши `3`, `8`, `4`;
- альтернативные коды `0x08`, `0x0A`, `0x02` дают те же логические клавиши `3`, `8`, `4`;
- состояния автомата: idle → press → hold/repeat → release;
- счётчики `0x28` (40) и `0x96` (150) — пороги long-press/repeat в циклах задачи, не миллисекунды;
- GPIO5 и GPIO14 отдельно конфигурируются через ISR callback (`FUN_40192e88`); после обнаружения разъёма `GND/S1/KA/KB` это с высокой уверенностью квадратурные фазы энкодера. Точное направление `KA/KB` остаётся откалибровать.

Внутренние incident-коды кнопочного пути: `0xF0`, `0xF2`, `0xF7`, `0xFE`. Обычные события очереди: 1/2/3/4/5. Для собственной прошивки безопаснее реализовать логический слой `KEY_MAIN`, `KEY_LEFT`, `KEY_RIGHT`, `ENCODER_CW`, `ENCODER_CCW`, `KEY_LONG`, а аппаратную карту GPIO/touch уточнить прозвонкой и пассивным логом.

Статика подтверждает три логических touch-кнопки, но не позволяет честно назвать `3/4/8` «левая/правая/центральная» и не доказывает, что пользовательский энкодер реализован чистым quadrature-сигналом. Это один из пунктов, который закрывается только наблюдением реальных линий при вращении ручки.

## 10. Белая подсветка и нижние LED

Программный SPI-подобный драйвер вызывается как `FUN_401c0870(0x11, 0x10, 4, 0, 7)`, то есть использует GPIO17, GPIO16 и GPIO4. В логическом байте `DAT_3ffc0dd2` есть минимум три управляемых бита:

- bit 0: `FUN_40192ef0` on / `FUN_40192f24` off;
- bit 1: `FUN_40192f50` on / `FUN_40192f78` off;
- bit 2: `FUN_40192fa0` on / `FUN_40192fc8` off.

`FUN_40192ff0(level)` задаёт 9 ступеней уровня 0…87. Таблица интенсивностей:

```text
(0,0,1), (0,8,1), (0,12,1), (0,14,1), (0,15,1),
(8,15,1), (12,15,1), (14,15,1), (15,15,1)
```

`FUN_4019305c` реализует мигание: при первом событии отправляется выбранный уровень, через 10/20 шагов канал выключается или повторно включается.

`DAT_3ffc047e` и `FUN_40152df8` управляют двумя старшими используемыми битами третьего байта именно из Wi‑Fi state machine. С учётом официальной схемы панели это два цвета нижнего Wi‑Fi LED; соответствие `bit1/bit2 ↔ blue/orange` остаётся определить коротким поканальным тестом. GPIO22/GPIO32 — отдельная пара прямых UI-выходов: они не относятся к OLED reset/DC и переключаются в режимах меню/таймера. Вероятнее всего, это подсветка боковых кнопок/таймерный индикатор, но точная физическая карта требует поканального теста.

## 11. Пищалка

`PeriodBuzzerTask` (`FUN_40192d0c`) получает очередь `_DAT_3ffcfc50`.

- коды 0…7 выбирают таблицу паттерна;
- `0xF1` выбирает специальный паттерн;
- `FUN_401be66c` исполняет массив троек `tone_parameter, pause1, pause2`, завершённый нулевой тройкой;
- `FUN_401be578` настраивает timer/PWM;
- инициализация `FUN_401be64c(0xFFFFFFFF, 0x17)` и `FUN_401c4930(0x17, 0)` указывают на GPIO23.

Для своей прошивки можно сохранить только абстракцию `beep(pattern)` и заменить таблицу частот/длительностей. Физический GPIO23 следует подтвердить прозвонкой, если плата будет перепаиваться.

## 12. Связь со снятым тепловым тестом

В тесте 2026-08-15, ручной уровень 99 и большая кастрюля:

- IGBT: 51 → 60 °C за 42.0 s, 70 °C за 67.0 s, 80 °C за 88.1 s, 90 °C за 111.4 s, 100 °C за 134.5 s;
- автоматическое отключение: 151.5 s, IGBT 107 °C, нижний NTC 96 °C, status 8 / error 7 / fault 7;
- кратковременный пик IGBT 109 °C после снятия мощности;
- вентилятор стал неслышен примерно при 54…55 °C IGBT, в то время как нижний NTC был около 88 °C.

Эта запись подтверждает плавность IGBT self-check и реальность E-07. Она **не** доказывает достаточность воздушного потока под нагрузкой. Последующий синхронный I²C/SOC-тест 2026-08-22 окончательно привязал `0x23` к IGBT, а `0x24` к нижнему NTC.

### 12.1. Синхронная runtime-корреляция 2026-08-22

В 180-секундном пассивном захвате с ручными уровнями 15, 30 и 55 одновременно записывались все I²C-кадры и read-only SOC/self-check:

- `0x23 raw ↔ IGBT`: Pearson `-0.9879`, RMSE линейной аппроксимации 0.70 °C на измеренном диапазоне 36…52 °C;
- `0x24 raw ↔ bottom NTC`: Pearson `-0.9933`, RMSE 0.91 °C на диапазоне 39…64 °C;
- `0x22` равен сетевому напряжению минус 50 для данной ревизии: raw 183…187 соответствовал self-check 233…237 V;
- Start: `W0D=A1`, `W00=01`, плавный `W0C 1→6→9→11→13→15`;
- переход 30→55 кратко прошёл gear 56 и дал `W0D C1→E1→C1`, чем runtime подтвердил порог кольцевого автомата;
- Stop: `W0D=00`, затем примерно через 50 ms `W00=00` и `W0C=00`;
- реальный ручной нагрев проходил при MIoT `On=false`; это свойство не является эквивалентом кнопки Start.

Полный отчёт и исходный `.sr`: `diagnostics/i2c_2026-08-22_pass6_manual_start/`.

### 12.2. Полный runtime pass 8: кольца, NoPan, Pause и Standby

В чистом 360-секундном захвате `20260822_1657_logic_mcl02m_cle` получено 13 680 кадров без ошибок checksum. Подтверждён 500-ms heartbeat: чтения `0x26,0x27,0x20…0x25`, затем записи `0x0D/0x00/0x0C`.

Главные результаты:

- 7-битный адрес — `0x2A`; wire bytes `0x54` write / `0x55` read;
- gear `1…35 → W0D=A1`, `36…55 → C1`, `56…99 → E1`;
- NoPan начинается с `R20=02`; после шести последовательных чтений за 2.769 s интерфейс переводит `W0D A1→80`, сохраняя `W00=1` и прежний `W0C`;
- первое восстановившееся `R20=00` возвращает топологию через 0.444 s, после чего UI автоматически снимает E02 и продолжает нагрев;
- Pause и полный Standby дают силовой плате одинаковый Stop: `W0D=0`, примерно через 50 ms `W00=0`, ещё через примерно 4 ms `W0C=0`;
- при Pause вентилятор продолжал работать; после полного Standby он работал ещё 72.37 s и стал неслышен при устойчивых 55 °C IGBT и около 94 °C нижнего NTC;
- `R21` имеет сильную связь с нагрузкой/gear (Pearson `+0.8405`) и падает примерно до 3 при NoPan;
- `R26=2` устойчиво совпадает с активным нагревом, `R26=0` — с NoPan/Pause/Standby;
- одиночный read `0x21` вернул только ACK адреса без данных, но следующий цикл восстановился: драйвер должен поддерживать retry, а не аварийный Stop от одного пропуска.

Полный отчёт: `diagnostics/i2c_2026-08-22_pass8_clean_full_sequence/REPORT.md`. Краткая реализационная спецификация: `reports/MCL02M_I2C_PROTOCOL.md`.

## 13. Что можно перенести в свою прошивку уже сейчас

1. Драйвер I²C0 10 kHz с адресом `0x54`, checksum `value + register`, чтением `0x20…0x2F` и безопасным timeout/retry.
2. Нормализованный объект измерений: `status`, `bottom_ntc`, `igbt_selfcheck`, `aux0…auxN`, `power_feedback`.
3. Независимый safety layer: no-pan, open/short сенсора, расхождение каналов, IGBT overtemp, bottom overtemp, communication timeout.
4. Внешний контур мощности: gear 0…100, ступенчатая derating/hysteresis, выбор inner/outer/both; физическую ассоциацию 0x40/0x80 уточнить до запуска.
5. UI 64×48: framebuffer 64×6, страницы OLED, glyph-таблица для английского и русского алфавита.
6. Абстракции `key_event`, `led_channel`, `beep_pattern`, не завязывая новую логику на старые MIoT/recipe структуры.
7. Wi‑Fi можно подключить отдельным собственным протоколом после того, как локальный safety/actuator layer работает автономно.

## 14. Что ещё нужно закрыть измерениями

Только пассивные, без записи во flash и без управления нагревом со стороны анализатора:

1. **I²C no-pan закрыт:** runtime подтвердил `R20=02`, debounce шесть samples, `W0D=80` search state и автоматический возврат. Осталось только активное воспроизведение в собственной прошивке после отдельного разрешения.
2. **Кольца:** пороги `35/36` и `55/56` и управляющие байты `A1/C1/E1` закрыты. На отключённой от сети силовой части прозвонить дорожки/разъёмы; затем тепловизором или токовым измерением физически назвать A/B внутренним/внешним кольцом.
3. **Температуры:** физическая карта подтверждена: `0x23=IGBT`, `0x24=bottom NTC`. Для собственной прошивки осталось извлечь/перенести обе штатные lookup-таблицы целиком и проверить крайние коды open/short.
4. **Вентилятор:** pass 8 подтвердил автономную работу в Pause/Standby и отключение около 55 °C IGBT. Измерить напряжение, PWM и ток на разъёме при росте температуры, потому что снятый вентилятор исправен только при 5…7 V и срывается выше 7.5 V. Команды override не посылать; в ESP32-дампе fan-драйвера нет.
5. **UI/LED:** прозвонить GPIO17/16/4, GPIO22/32, GPIO23, GPIO26/27/25 к разъёмам; при снятом питании определить цвета и полярность.
6. **Touch/энкодер:** пассивно снять линии при нажатии и вращении; подтвердить, являются ли `3/4/8` touch-кнопками, quadrature-каналами или кодами внешнего controller.

До этих измерений нельзя безопасно утверждать физическое имя каждого I²C-канала, кольца и LED-бита. Никакая из перечисленных проверок не требует записи в flash или изменения прошивки.

## Итог

Для собственной англо-русской прошивки уже известна большая часть интерфейсного контракта: шина, checksum, регистры, три команды записи, кодирование колец, gear-ограничители, температурные аварии, no-pan debounce, framebuffer и периферийные задачи. Неизвлечённой остаётся прошивка силового MCU (`mimcu` в ESP32 dump заполнен `FF`), поэтому его внутренняя физика PWM, точные таблицы NTC и fan-drive не восстанавливаются статически. Это не мешает написать собственный UI/сеть/логический safety layer, но перед первым управляемым запуском нужно закрыть физическую карту сенсоров, колец и вентиляторных линий пассивными измерениями.
